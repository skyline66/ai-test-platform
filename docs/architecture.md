# 架构：这套「大框架」到底分几层

> 本文档对应文章《AI测试54：Playwright+PO 到 AI 测试平台》的骨架，
> 把它拆成可执行的四层 + 平台四块，并说明每一层为什么存在。

## 一句话

**UI 自动化的成本不在「写第一版」，在「改第 41 次」。**
所以这套框架的每一层都在回答同一个问题：*下次改的时候，我只需要改几个地方？*

| 问题 | 由谁回答 |
| --- | --- |
| 页面改了，定位改哪？ | `pages/`（唯一允许出现定位的地方） |
| 挂了怎么知道挂在哪？ | `utils/evidence.py` + `atp/report.py`（截图 / URL / 控制台 / 归因） |
| 谁来跑、什么时候跑？ | `atp/runner.py` + `atp/scheduler.py` |
| 新需求谁先写第一版？ | `atp/authoring.py`（模板兜底，模型可选） |
| 改版后二十条定位全红怎么办？ | `atp/locator_doctor.py`（一次快照批量重建） |
| 服务器上为什么挂了、本机为什么好？ | `atp/config.py` + `Dockerfile`（环境锁死） |

---

## 一、四层分工（纪律比架构重要）

```
tests/     只写「步骤」和「断言」      ← 被执行的资产
pages/     只写「定位」和「动作」      ← 页面改了只改这里
utils/     配置、日志、数据、现场保全  ← 公共能力，不含业务
atp/       平台：调度 / 分析 / 管理 / 环境  ← 不含用例
```

三条边界，都能被 `python -m atp lint` 检查出来：

1. **用例层不许出现定位。** `tests/` 里 `grep` 得到 `locator(`、`xpath`、`nth-child`、`#id` 即违规（TESTS-001）。
2. **用例层不许直接操作元素。** `.click(` / `.fill(` 一律封装进页面对象（TESTS-002）。
3. **页面对象不许写断言。** 页面只回答「怎么点」，不回答「点了算不算对」（PAGES-001）。

> 能 grep 出来的规范，才是能执行的规范。剩下靠自觉的规范，半年后就不存在了。

## 二、平台四块（按重要性排，不是按做起来爽的顺序）

```
┌──────────────────────────────────────────────────────────────┐
│ ① 执行调度  runner.py + scheduler.py                          │
│   每次运行一个目录、产物隔离、同一时刻只跑一份                │
├──────────────────────────────────────────────────────────────┤
│ ② 结果分析  triage.py + report.py                             │
│   失败归因（规则优先，模型补充）+ 单文件自包含报告            │
├──────────────────────────────────────────────────────────────┤
│ ③ 用例管理  registry.py + store.py                            │
│   静态扫描 tests/ 做索引，草稿单独隔离，不维护第二份清单      │
├──────────────────────────────────────────────────────────────┤
│ ④ 环境与数据 config.py + Dockerfile + utils/data.py           │
│   浏览器版本 / 时区 / 字体 / 代理 / 测试账号，全部固化        │
└──────────────────────────────────────────────────────────────┘
```

**为什么不从「用例管理」做起**：很多人先做用例列表和看板，做完发现最痛的其实是
「谁在什么时候跑、挂了通知谁」。执行调度排第一，是因为它决定平台有没有人被用。

**为什么不做权限 / 多租户 / 大屏**：这些是「有人天天用」之后才需要的。
先让它每天跑一次冒烟，跑两周没人骂，再谈扩展。

## 三、数据流

```
 一句话需求 ──► authoring ──► tests/drafts/test_draft_*.py （草稿，不进冒烟集）
                                      │
                                      ▼ 人工确认、补业务断言、去掉 draft 标记
 tests/ ──► registry（索引）──► runner（pytest 子进程）
                                   │         │
                                   │         └──► utils/evidence.py
                                   │              截图 + URL + 控制台 → evidence/
                                   ▼
                            pytest-report.json（结构化）
                                   │
                    ┌──────────────┴──────────────┐
                    ▼                             ▼
              store（sqlite 归档）          triage（归因）
                    │                             │
                    └──────────► report.html ◄────┘
                                     │
                                     ▼
                           CLI / HTTP API / 网页
```

关键点：**用例的真源永远是 `tests/` 里的 Python 文件**，平台只做索引与归档。
数据库里没有一份「用例表」，所以不存在表与代码漂移的问题。

## 四、为什么是这些技术选择

| 选择 | 理由 | 代价 |
| --- | --- | --- |
| sqlite 而非 Postgres | 单机平台，一个文件就是全部状态，备份=复制 | 多人并发写要换库 |
| 不用 ORM | 早期最不需要的就是「表结构比用例还复杂」 | 复杂查询要手写 SQL |
| 模板兜底 + 模型可选 | 没配 API key 也必须能跑，CI 不能依赖外部模型 | 生成质量有上限 |
| 归因规则优先 | 可解释、可复现、零成本；模型只在置信度低时补措辞 | 新失败模式要加规则 |
| 自渲染 HTML 报告 | Allure 管「可追溯」，平台管「一眼看懂」，两者不冲突 | 多维护一个模板 |
| 单文件前端（无构建） | 平台早期不该有前端构建链 | 复杂交互会受限 |

## 五、已知限制 / 下一步

- **没有通知**：挂了不出声。下一步接企业微信 / 飞书 webhook（`triage` 已有结构化结果，接起来只是拼一条消息）。
- **归因靠规则**：新失败模式需要补 `atp/triage.py` 里的 RULES。
- **草稿不自动进冒烟集**：这是刻意设计，不是缺陷。人工确认是这条流水线的一部分。
- **没有多环境切换 UI**：目前靠 `ATP_BASE_URL` 环境变量，够用但不够顺手。
- **并发**：`RUN_LOCK` 明确禁止并行跑，正确但不快；要并行得先做到用例级隔离。
